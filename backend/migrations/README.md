# 上线 SQL

PostgreSQL 版本固定为 18.3，与线上一致；开发及隔离测试统一使用 `postgres:18.3-alpine`。目标数据库应已创建，通常使用 `public` schema；执行 SQL 的连接应与应用使用相同的数据库及 schema，并具备相应建表和修改表权限。本文的结构迁移不会升级 PostgreSQL 引擎版本，旧版本数据库须先单独完成版本迁移。

## 执行入口

| 文件 | 用途 |
| --- | --- |
| `release.sql` | 可独立导入的上线 SQL，按顺序合并 000 历史基线和 001–026，支持空库初始化与本项目旧版本升级 |
| `verify.sql` | 只读核对 21 张表及所需字段，返回数据库、schema、缺失项和状态 |
| `schema.sql` | 当前全部 21 张表的完整结构快照，包含字段、默认值、约束、索引和中文表注释，可独立初始化空库 |
| `inspect.sql` | 只读导出现有数据库结构为 JSON，用于上线前与项目快照比较，不查询业务行 |
| `upgrade-from-002.sql` | 2026-09-16 上线包：将截图中的旧版八张表（000–002）升级至 025，内置事务前后检查 |
| `000_initial_schema.sql` | 不可变历史基线，保留最早 3 张基础表，作为旧库升级入口 |
| `001_wallet_and_renewals.sql` | Session、续订日期、钱包、充值、流水、续订与日期审计 |
| `002_payment_quantity_and_history.sql` | 充值数量、单价、价格 ID，以及扣款记录的账号名称和时长快照 |
| `011_table_comments.sql` | 为已有数据库补齐 12 张表的中文说明 |
| `012_soft_delete_timestamps.sql` | 全表统一时间字段、软删除索引及历史触发器 |
| `014_application_integrity.sql` | 移除历史外键、物理删除防护触发器及对应函数，应用层维护关联和软删除 |
| `015_recharge_operations.sql` | 充值运营、权限、认证、退款、预授权及对账扩展，共 20 张表 |
| `018_admin_two_factor.sql` | 管理员验证器加密密钥、待绑定过期时间、启用时间和已消费时间步 |
| `013_application_timestamps.sql` | 移除时间维护触发器，由应用显式维护更新时间及软删除时间 |
| `025_table_ids.sql` | 为钱包、钱包充值订单、历史续订和认证限流补齐独立自增 ID 主键，保留业务唯一性 |
| `026_account_payment_card.sql` | 账号默认付款卡及活跃绑定索引；沿用 renewal_enabled 记录是否续订及提醒，旧账号默认不绑卡 |

账号列表排序、是否续订开关和默认付款卡功能需先应用 026（或最新 `release.sql`）再部署服务。已执行到 025 的数据库只需执行新增迁移；截图专用 `upgrade-from-002.sql` 仍固定到 025，使用后须继续应用 026。迁移不回填或猜测付款卡，不改写订单、余额、历史流水及原续订设置。实际数据库执行仍需单独授权。

推荐在部署新服务前执行 `release.sql`。已有项目库无需重新建库或清空数据；重复执行会跳过已存在的表和字段。不要再额外执行一遍编号迁移。

若需先核对线上差异，执行 `inspect.sql` 并保存完整的 `schema_report` 结果，再根据实际差异准备增量上线 SQL。默认检查 `public`，其他 schema 修改脚本开头的数组；返回字段定义及顺序、约束、索引、注释、序列定义与归属、非内置触发器、自定义函数/存储过程、视图、枚举/域、行级策略及扩展版本。查询使用只读事务，不导出业务行或序列当前计数。SQL 客户端应导出完整单元格，避免显示长度截断；也可通过已配置连接的 `psql -X -qAt -v ON_ERROR_STOP=1 -f "backend/migrations/inspect.sql" > "online-schema.json"` 保存文件。该报告用于结构比对，不替代数据库备份；需要数据回填的升级仍须单独评估历史数据。

## 截图旧库上线包（000–002 → 025）

`upgrade-from-002.sql` 针对截图中的 `users`、`chatgpt_accounts`、`email_codes`、`wallets`、`topup_orders`、`wallet_ledger`、`account_renewals`、`renewal_date_audit` 八张表，字段与 000–002 一致。截图未显示约束、索引及默认值，按项目原版定义整理；若线上存在手工改动，应先用 `inspect.sql` 核对，不能只凭字段截图确认全部结构一致。

该文件固定对应 025 版本，从已有 release 的 003–025 段整理，省略已被后续迁移淘汰的外键、函数和触发器创建语句，保留已知旧约束的移除及业务唯一索引。继续应用 026 及后续迁移后的字段定义、默认值、约束、索引与当前快照的一致性由隔离测试验证。它不改写历史迁移，也不替代未来版本的增量迁移；已执行本包时不要再把 release 或 003–025 当作下一次升级。

执行顺序：备份 → 停止旧应用、任务等写入 → 在 public schema 的目标数据库完整执行文件 → 确认所有语句无错误且 COMMIT 成功 → 依次应用 026 及后续新增迁移 → 执行 `verify.sql` 得到 21 行 OK → 部署新版应用。脚本锁住旧八表，锁等待 5 秒、单语句 5 分钟；前置字段类型检查和提交前结构检查通过 INSERT 写入会话临时校验表，失败会触发 aitok_upgrade_schema_check 约束，使整个事务不能提交。脚本不返回查询结果集，兼容将整段迁移按更新语句执行的 SQL 客户端；临时校验表在结束前移除，回滚或提交后均不留存。客户端必须遇错停止，失败后执行 ROLLBACK 并检查首个错误，不要跳过报错语句。若客户端提示“传回预期之外的结果”，不能据此判断服务端是否已提交；先在同一连接单独执行 ROLLBACK，再单独运行 verify.sql 核对，仍有 INVALID 时对照缺失项确认旧升级包及后续迁移的执行状态，禁止去掉事务或结构校验。

保留原账号、密码哈希、Session 密文、余额、订单号、流水、到期日及原创建时间；为缺失 ID 的行分配 ID，缺失的历史时间使用迁移时间，新增角色默认为用户。无需填写真实卡号、密钥或导入测试数据。已有表不重排物理列；新权限、银行卡、订单、汇率等结构补齐后共 21 张表。`TestLegacyScreenshotUpgrade` 验证八表旧数据保留、重复执行 ID 稳定、前置不匹配与未知外键导致升级失败并可整体回滚；结构测试同时比较本包与 schema.sql 的最终定义；TestLegacyUpgradeReturnsNoResultSets 从 PostgreSQL 协议层验证整段执行及重放都不产生行结果集。

`schema.sql` 是阅读当前结构和初始化空库的入口，所有表直接展示最终字段，不需要读者拼接历史 ALTER。它不负责升级已存在的旧表；`CREATE TABLE IF NOT EXISTS` 不会补齐旧表字段，因此旧库必须使用增量迁移或 `release.sql`。

快照中所有表的最后三个字段统一为 `created_at`、`updated_at`、`deleted_at`，表级约束列在字段定义之后；`verify.sql` 的字段清单采用同一顺序。现有历史迁移按原顺序保留，`release.sql` 仍从历史迁移生成，因此实体表的物理列顺序可能与快照不同。仅整理快照不产生数据库迁移，也不会移动已有数据库中的列；实体列重排需另行迁移。结构一致性测试比较字段定义、约束及索引，另对快照初始化后的时间字段顺序做检查。

在项目根目录，使用已经配置好的 PostgreSQL 客户端连接参数执行：

```bash
# PGHOST、PGPORT、PGDATABASE、PGUSER 或 PGSERVICE 指向目标数据库。
# 密码使用 .pgpass 或客户端提示输入，不写在 SQL 中。
psql -X --set=ON_ERROR_STOP=1 --file="backend/migrations/release.sql"
psql -X --set=ON_ERROR_STOP=1 --file="backend/migrations/verify.sql"
```

也可以在数据库管理工具中选中目标数据库，整体执行 `release.sql`，然后执行 `verify.sql`。遇到错误应停止执行并回滚事务；不要忽略错误后继续执行剩余语句。文件已包含事务，不再套用 `psql --single-transaction`。

合并 SQL 使用一个事务；锁等待上限 5 秒、单条语句上限 5 分钟。超时或任何语句失败时，本次事务不提交，排查后可以重新执行。文件不包含 `CREATE DATABASE`、数据库用户、权限、测试账号或充值数据。服务部署脚本 `scripts/deploy.sh` 不执行这些 SQL。

`verify.sql` 应返回 21 行 `OK`，缺失字段、无效时间字段和触发器数组均为 `{}`，`invalid_id` 均为 `false`。它检查表和字段是否存在、每张表的 `id` 是否为非空 BIGINT 单列主键且具备所属序列和 nextval 默认值、三个时间字段的类型/默认值/NULL 约束以及所有触发器和外键是否已移除，不会修改数据；其他字段类型及业务唯一约束仍需单独核对。`IF NOT EXISTS` 不会修复手工改过的同名对象；这类库应与 `release.sql` 中的定义单独比对。

## 表与历史数据

| 表 | 内容 |
| --- | --- |
| `users` | 平台用户和密码哈希 |
| `chatgpt_accounts` | 用户绑定的 ChatGPT 账号、加密 Session 和续订日期 |
| `email_codes` | 邮箱验证码哈希及有效期 |
| `wallets` | 用户代币余额 |

| `wallet_ledger` | 充值及续订产生的余额流水 |
| `account_renewals` | 账号续订、扣款、日期及账号名称快照 |
| `renewal_date_audit` | 管理员修改续订日期的审计记录 |
| `account_groups` | 用户的账号分组 |
| `addresses` | 账单姓名、地址、所属用户及完整来源资料 |
| `bank_cards` | 加密银行卡、平台、备注和 USD 美分余额 |
| `bank_card_ledger` | 银行卡初始余额、存入、开通支出及交易后余额流水 |

- 超管账号由后端首次成功登录时创建，用户名和密码来自环境配置，不在 SQL 中插入。

- 旧充值的 `quantity` 默认为 1，`unit_amount_minor`、`price_id` 允许为空；应用显示单价时回退到原订单总额。
- 旧续订的 `account_label`、`months` 允许为空，应用优先回退到当前账号名称，无法还原的时长显示“—”。不回填无法确认的历史信息。
- 续订和日期审计中的 `account_id` 不关联级联删除，账号删除后历史记录仍保留。

## 维护方式

**任何表结构变更都必须同步更新 `schema.sql`**，包括表、字段、默认值、约束、索引及注释。每张表必须保留中文 `COMMENT ON TABLE`。同时新增编号迁移用于旧库升级，不修改已执行的历史迁移。规范见根目录 [agent.md](../../agent.md)，由 [AGENTS.md](../../AGENTS.md) 引入。

每张表必须有独立的 `id BIGSERIAL PRIMARY KEY`，每行 ID 非空、表内唯一且创建后不变；业务字段或联合主键不能替代 `id`，原业务唯一性及幂等约束必须保留。

上线文件仅从不可变历史基线 `000_initial_schema.sql` 和后续编号迁移生成，不拼接完整快照，避免在旧库尚未添加字段时提前创建索引。同步快照并新增编号迁移后，在项目根目录重新生成上线文件：

生成器省略已被 012 替换的旧地址、分组全量唯一索引，以及被 015 替换的旧账号单次扣款索引，直接使用迁移末尾的活跃记录唯一索引，避免已有软删除同名数据时重放失败。历史迁移原文件保持不变，已升级数据库不应手动从 000 开始逐个重放，应执行生成的上线 SQL 或尚未应用的新迁移。

```bash
bash scripts/build-release-sql.sh > "backend/migrations/release.sql"
```

生成脚本只读取本地 SQL 并输出文本，不读取 `.env`，不连接数据库。新的编号迁移应继续使用能在单个事务中执行的语句；如果包含 `CREATE INDEX CONCURRENTLY` 等禁止在事务中执行的操作，应另行安排上线步骤，不能直接加入此合并入口。修改表或字段时同步更新 `verify.sql` 和本说明。

配置隔离测试用 `TEST_DATABASE_URL` 后，运行 `go test ./cmd/server -run TestSchemaSnapshotMatchesMigrations`。测试在事务中创建临时表并回滚，比对完整快照、编号迁移、生成上线 SQL、旧基线升级和重复执行后的字段、默认值、约束、索引、表注释、函数与触发器，不修改业务表。

## 银行卡平台与备注（008）

`008_bank_card_platform_and_notes.sql` 为 `bank_cards` 增加 `platform`（最多 80 字）和 `notes`（最多 1000 字），均为非空文本、默认空字符串。旧银行卡无须回填，平台选项按用户从已有银行卡中去重读取。先执行迁移再部署服务；锁等待超过 5 秒会失败回滚。

应用回滚时保留新增列即可，旧版本忽略这两个字段。结构回滚需要另建前向迁移删除列，会永久丢失平台及备注，应备份并明确确认后执行，不自动回滚数据。

## 用户角色（009）

`009_user_roles.sql` 增加 `users.role`，默认 `user`，允许历史空值；约束只接受 `user`、`admin`、空字符串或 NULL，超管身份独立判定。旧用户无须批量更新。应用权限变更实时生效。先迁移再部署；如回滚应用版本，保留 role 字段。结构回滚需单独确认并创建删除该列的前向迁移，会丢失已分配角色，不自动执行。

## 银行卡 USD 对账单（010）

`010_bank_card_ledger.sql` 增加卡片 USD 美分余额与 `bank_card_ledger` 流水表。旧卡初始记账余额为零，不回填历史资金；首次存入生成初始余额流水。存入、扣款和交易后余额原子提交，按卡加锁，重复请求幂等；010 的单账号终身一次限制已由 015 调整为按周期防重。账号名称、邮箱、原价 PHP 8,919.64 以快照保存；实际 USD 扣款由操作者按卡平台账单确认，包含实际汇率及手续费。对账时间展示为 UTC+8。

流水仅可追加，不提供修改或删除接口；有流水的卡片禁止更换卡号；012 之后删除卡片仅标记软删除，保留余额与流水，避免对账记录丢失或转移到另一张卡。银行卡与流水接口现在仅管理员可用，普通用户仅能查看和添加自己的账号。余额及流水不与代币钱包混用，不会发起真实转账或支付。

先迁移再部署后端及前端。迁移锁等待上限 5 秒，不包含业务数据更新。应用回滚保留新增结构即可；结构回滚会丢失财务记录，明确标记为不可自动逆向回滚，需另建前向迁移、备份并单独确认。

## 统一时间字段和软删除（012）

所有 12 张表统一包含 `created_at`、`updated_at`、`deleted_at`，类型为 `TIMESTAMPTZ`；前两者非空、默认 NOW()，删除时间默认为 NULL。012 曾通过更新触发器维护时间；013 移除该触发器后，所有应用更新显式写入 `updated_at=NOW()`，且不修改 `created_at`。历史上未记录的时间使用迁移时刻，不推算过去时间；已有时间字段保持原值。

业务删除同时更新 `deleted_at` 和 `updated_at`，记录继续保留。012 曾安装禁止 DELETE/TRUNCATE 的触发器并移除物理级联；014 将这些触发器和外键完全移除，关联校验与软删除由应用负责。删除分组时在同一事务内解除活跃账号的分组绑定。查询、搜索、选项及普通更新过滤已删除记录，用户被删除后旧令牌失效。银行卡可软删除，历史对账接口仍可只读访问，不能再为已删除卡记账。

邮箱、分组名称、地址位置、卡号指纹改为仅对活跃记录唯一，删除后可用新 ID 重新添加；验证码新增独立 id 主键，消费时软删除，新的验证码不覆盖已消费记录。金融流水及支付幂等约束仍覆盖所有历史记录，删除不允许重复入账。银行卡只读审计及幂等检查明确保留对历史记录的访问。

迁移涉及索引和约束切换，应先停止应用写入，再执行未应用的 011–013，最后部署匹配的新版本。事务锁等待上限 5 秒，失败会回滚；不清空表、不删除业务数据。旧代码的真实删除及旧 ON CONFLICT 目标与新结构不兼容，不直接回滚旧应用。结构逆向回滚需要新的迁移方案和授权，本项目不自动执行。

## 应用维护时间（013）

12 张业务表的字段已由 012 补齐，013 不重复改写历史迁移。013 仅移除 12 个时间维护触发器及对应函数；历史外键和禁止物理删除触发器随后由 014 移除，最终快照不再包含这些对象。

创建记录使用字段默认时间；账号 Session、登录时间、分组绑定/解绑、续订日期、用户密码/角色、充值订单状态、钱包余额及地址/银行卡更新均由应用在同一条 SQL 中维护更新时间。软删除同时写入两个时间，并过滤已经删除的记录。验证码消费、过期或未消费验证码被重新签发替代时均保留原行；同邮箱同用途通过事务锁串行换码，每次签发使用新 ID。

上线前停止旧应用写入，执行新迁移或生成的 `release.sql`，再启动匹配的后端；不要在移除触发器后继续运行依赖触发器的旧版本。三个字段无需额外数据回填。

运行后端测试时配置隔离用 `TEST_DATABASE_URL`；软删除、验证码重发和密码/角色、账号、支付等更新测试应在无时间触发器的临时表上通过，核对创建时间保持、更新时间推进、软删除原行保留及历史记录不可覆盖。

## 充值运营与权限（014–015）

历史账号会员状态不自动标记为核验成功，历史卡片不填入猜测余额，套餐初始为空。015 历史版本支持细分管理员权限；当前版本按角色统一授权，管理员拥有所有业务权限，历史 permissions 字段仅兼容保留。历史银行卡单次扣款没有可靠周期，保留原始记录；新充值按邮箱和周期防重，真实续费可记下一周期，冲正释放对应周期但不释放原交易号。

验证包括空库快照、编号迁移、旧基线升级、release 重放，以及带软删除重名记录、多周期和冲正历史的重复升级。测试使用连接内临时表，不更改真实业务表。

## PHP 套餐每日汇率（016）

新增 `exchange_rates`（第 21 张业务表）保存 PHP/USD 汇率历史、生效时间、来源及三个时间字段；新增 `recharge_packages.auto_usd`，默认 FALSE，旧套餐继续使用固定 USD 售价。无外键、函数或触发器，不改写订单及资金记录，也不在结构 SQL 中导入价格。

应用启动时补同步，之后 UTC+8 每天 09:00 从 ExchangeRate-API 更新，失败每 30 分钟重试；事务 advisory lock 防多实例同时写入。成功只追加汇率历史，查询套餐时实时折算；新订单保存当时的价格和完整汇率信息，重复下单请求继续返回原快照。汇率数据或同步时间超过 48 小时视为过期，保留显示并禁止新自动定价订单。

部署顺序：备份 → 经确认执行 016 → verify.sql 返回 21 行 OK → 部署前后端 → 等待汇率同步 → 运行套餐导入脚本预览、录入并核对。旧版本不识别自动定价，不能继续接受该类套餐的新订单；如需应用回退，应先停止自动定价套餐下单并保留新增表列。结构回退只能经授权另做前向迁移，不能删除汇率和订单历史。

## 人民币参考折算（017）

`017_exchange_rates_cny.sql` 将现有汇率表的币种约束扩展为 USD/CNY，并分别校验 PHP→USD、PHP→CNY 的合理数值范围；表数量和字段不变，无数据回填。每日任务在同一事务内写入两个币种，来源、生效时间和同步时间一致；旧 USD 历史保留，新服务启动时自动补齐完整批次，后续每天 UTC+8 09:00 更新，失败每 30 分钟重试。

先备份并经确认执行 017，再部署匹配前后端。`verify.sql` 继续核对 21 张表并检查两项汇率约束均支持 CNY。重复升级与带 CNY 记录的重放需在隔离临时表测试。旧版本可忽略 CNY 历史，但不再同步人民币；回退应用时保留扩展约束和历史记录，不自动做结构逆向回退。

## 订单结束状态与周期释放（019–020）

019 新增 `recharge_orders.order_status`（active / refunded / discarded），调整订单周期唯一索引为仅约束正常订单；银行卡周期索引只约束无订单的直接扣款，关联订单仍受每订单唯一扣款和应用层周期锁约束。订单号、实际交易号及资金流水的唯一约束保持覆盖全部历史。

020 单独回填历史状态：已全额退款或已有 refund_note 的订单设为 refunded，原已取消订单设为 discarded；只更新仍为 active 且未软删除的订单，并增加 version、维护 updated_at。保留旧订单号、创建时间、收款/开通状态及全部金额余额，重复执行不会再次更新已结束订单。

不自动逆向迁移：新系统允许结束订单后创建同周期订单，旧索引无法容纳这些历史记录。不能直接回滚旧服务，应保留结构、余额和历史并采用前向修复。release 生成器跳过 015 的旧周期索引定义，避免带重建订单和扣款历史的重复升级失败。结构回归覆盖该场景，数据回填测试验证状态、资金记录及幂等性。

## 全表独立 ID（025）
